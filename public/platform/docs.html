DEVELOPER DOCUMENTATION

Network AI in your application.

Sign in with email or Google, create a key, and call an available model. KAI Core does not need to be installed or running.

1. Create an API key

Open your dashboard and select API keys. Choose the credit balance, daily usage limit, lifetime, and permissions. A wallet is optional for free-only access. Your full key is shown once.

Send the key as Authorization: Bearer YOUR_KAI_API_KEY Keep it on your server or in a secure secrets store. Do not embed it in a public website. Cookie sessions are for the dashboard; API endpoints require an API key.

2. Choose an available model

curl https://credits.koinosai.com/v1/models \
  -H "Authorization: Bearer $KAI_API_KEY"

Use an exact model ID from this response. Availability depends on independent providers and may change between listing a model and sending a request.

3. Send a text chat request

curl https://credits.koinosai.com/v1/chat/completions \
  -H "Authorization: Bearer $KAI_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: my-request-0001" \
  -d '{"model":"MODEL_ID_FROM_LIST", "messages":[
    {"role":"user", "content":"Write a short welcome message."}
  ], "max_tokens":256}'

Supported fields: model, messages, max_tokens (or max_completion_tokens), stream, stream_options Messages support text with system, user and assistant roles. The current endpoint does not support tools, images, audio, embeddings, the Responses API, or sampling controls. Unsupported fields return an error.

from openai import OpenAI
import os

client = OpenAI(
    base_url="https://credits.koinosai.com/v1",
    api_key=os.environ["KAI_API_KEY"],
    timeout=240.0,
    max_retries=0,
)
model = client.models.list().data[0].id
reply = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Hello!"}],
    max_tokens=256,
    extra_headers={"Idempotency-Key": "my-request-0001"},
)
print(reply.choices[0].message.content)

For streaming, set "stream": true Responses use server-sent events with incremental choices[0].delta.content and end with data: [DONE]. Add "stream_options": {"include_usage": true} to receive a terminal usage event. Keepalive comments may appear while a provider prepares its model.

Credits and limits

One credit equals 100,000 USD atoms; 1,000 credits represent $1 of usage. Balances and credit limits use exact integer atom strings. Free allowance refreshes at 00:00 UTC, does not accumulate, and is shared across this verified account's web and API use. Eligible models, account limits, network budgets, and sponsorship availability all apply.

Each key is bound to either the account's free allowance or one linked payment wallet. Purchased balances are not merged across wallets. A linked wallet's existing purchased balance is shared with Core. A new API key does not create a new daily allowance.

Key daily ceilings cover free and purchased inference combined, including pending reservations. The admission date is UTC; unfinished older requests count until resolved. The gateway allows 60 requests per minute per account across keys and dashboard inference/billing calls. The existing network concurrency limits also apply.

Free-only keys stop when free credits cannot cover the request. When purchased usage is enabled, free credits are used first and the remainder comes from that key's selected wallet. Signing out of a browser does not revoke API keys; revoke keys from the dashboard.

Purchase credits through the API

  1. Link a Koinos wallet in the dashboard and create a key bound to it with billing:purchase.
  2. POST {"dollars":"5.00","intent_id":"64_LOWERCASE_HEX_CHARACTERS"} to /v1/credits/purchase-quote. Reuse that intent for a retry. The response contains the quote, exact KOIN amount, credited amount, expiration, and an unsigned transaction.
  3. Review and sign the returned transaction with the selected wallet. Submit those exact signed bytes to a Koinos mainnet RPC. The API key cannot sign or move KOIN. The dashboard handles this with Kondor.
  4. POST {"tx_id":"0x1220…"} to /v1/credits/purchases. Credits are added only after verified finality. Poll the balance or recheck the same transaction if confirmation is pending. Repeating confirmation cannot create duplicate credits.

Never submit a new payment merely because the broadcast response was lost. Keep the original transaction ID and check it. Card payments and automatic top-ups are not included in this version.

Retries and privacy

Use an Idempotency-Key of 8–128 letters, numbers, dots, colons, underscores or hyphens. Retry with the same key, model, message, streaming setting and token limit. The ID is scoped to the API key and payment wallet. A completed reply can be recovered while the existing encrypted reply retention permits; retrying it does not debit again. Changed request content is rejected. A cancelled or interrupted request may need a new ID; inspect usage before retrying.

Errors use an error.message object. Invalid/expired/revoked keys return 401, missing permissions return 403, key/account limits return 429, oversized payloads return 413, and invalid or unsupported requests return 400. Respect Retry-After when returned. A network failure after partial streaming may have charged the verified portion already delivered.

Network inference sends prompts through the scheduler and a serving provider. Gateway logs do not add prompt storage. The existing credit runtime temporarily retains encrypted replies for recovery and retains usage receipts. Browser playground history is held only in that page's memory.
